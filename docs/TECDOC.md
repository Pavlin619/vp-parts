# TecDoc — measured behaviour and feature detail

This was moved out of `CLAUDE.md`, which is loaded into every prompt and is for
conventions rather than feature specifics. Nothing here is obsolete: it is the
record of what the live Pegasus 3.0 endpoint actually does, measured by the
probes under `apps/api/scripts/`, and where a statement contradicts the XSD it
says so and gives the numbers.

`CLAUDE.md` keeps only the rules that apply to any TecDoc call. Read the section
here that covers the surface you are about to change, and add new findings to
this file rather than back to `CLAUDE.md`.

### TecDoc Pegasus 3.0 API integration

**Critical: TecDoc is NOT a REST API.** It is a JSON RPC service. Do not invent REST-style paths — they do not exist and calls will fail silently or with unexpected errors.

**Protocol:** All calls are `HTTP POST` to a single endpoint:
```
POST {TECDOC_BASE_URL}/services/TecdocToCatDLB.jsonEndpoint
```

**Request shape:** The function name is the top-level JSON key:
```json
{
  "getFunctionName": {
    "lang": "bg",
    "linkageTargetCountry": "BG",
    ...other params
  }
}
```

**Authentication:** `X-Api-Key: YOUR_KEY` HTTP header (correct as implemented).

**Required env vars:** `TECDOC_BASE_URL`, `TECDOC_API_KEY`.

**`provider` is optional, and a wrong one is worse than none.** The XSD marks `provider` ("Your assigned TecDoc Provider Id") required on every request type, but the live service does not enforce it: entitlement is resolved from `X-Api-Key`. Verified against the live endpoint with our key — a call omitting `provider` is answered in full, and one carrying a ProviderId that is not ours is refused `{"status":401,"statusText":"Access not allowed"}` regardless of how valid the key is. This is why `TECDOC_PROVIDER_ID` is optional in the Joi schema and omitted from the body when unset; never fill it with a placeholder to get past a validation error. `[VERIFY-TC]` Whether a real ProviderId scopes the assortment is unverified — we have never held one.

**Key functions used in this project:**

| Function | Purpose |
|---|---|
| `getLinkageTargets` | Manufacturers, model series, vehicle variants |
| `getArticles` | Assembly group tree, article list, article search by number |
| `getBrands` | Brand logos (future) |
| `getAutoCompleteSuggestions` | Search autocomplete (future) |
| `getArticleLinkedAllLinkingTarget4` | Compatible vehicles for an article (future, doc section 8.4) |
| `getKeyValues` | The full vocabulary of one key table, by `keyTableId` |
| `getManufacturers2` | Which vehicle makes TecDoc considers popular — see below |

**Where to verify the contract before implementing any TecDoc call.** Two documents are authoritative, and they answer different questions:

1. **The XSD** — `https://webservice.tecalliance.services/pegasus-3-0/services/TecdocToCatDLB.soapEndpoint?xsd=1` (no credentials needed). Every request and response type with its documented field semantics. Note the `.soapEndpoint` segment: the path without it returns 404. The JSON endpoint we actually call is the same contract, so this schema is authoritative for it too.
2. **Onboarding Guide — TecDoc Web Service (TecDoc Pegasus 3.0 API), version 3.0, 25/01/2022.** Worked request/response pairs for the flows this project is built on — §8.2 vehicle drill, §8.3 assembly-group drill, §8.5 number search — plus behaviour the XSD has no way to express, such as what a response looks like when a parameter is left at a sentinel value.

Use the XSD for *what a field is* and the guide for *what a call returns in practice*. **Where they disagree, the XSD wins**: it is served live, while the guide is a 2022 snapshot. Where the guide shows something the XSD does not mention, the guide stands — but say so at the point of use, because it is the weaker source.

- Interactive docs + test client: `https://webservice.tecalliance.services/pegasus-3-0/info/`
- Service Index tab: every function with full request/response parameter documentation
- Use the Test Client tab (needs a provider key) to verify actual response shapes before writing mapping code

**Never assume a field name or endpoint path.** Always check the XSD or the Service Index before adding a new TecDoc call.

**Mark what the schema cannot settle.** Some behaviour is not in the XSD — how repeated filters combine, whether an id is unique across trees, what a sentinel default means. Where the code had to assume, leave a `[VERIFY-TC]` comment stating the assumption and what breaks if it is wrong, so the next person able to probe the live endpoint can close it. Grep for `[VERIFY-TC]` to find the open ones.

**Close a marker by replacing it with the measurement, not by deleting it.** The assumption was worth writing down, so the answer is worth more: state what the call actually returned and how it was established, because the next reader's question is "how do we know?" and a bare assertion sends them back to the endpoint. Two of the closed ones contradicted the schema outright — `maxDepth`'s documented default and `includeCompleteTree`'s stated necessity — and only the recorded numbers stop that being re-litigated. A marker that is *still* open stays open: `provider` cannot be settled without holding a real ProviderId, so it keeps its comment rather than being quietly resolved in one direction.

#### The vehicle selector sells car and van parts, so it enumerates `'VL'`

**`LinkageTargetType.Vehicle` (`'P'`) is a union — passenger cars, motorcycles *and* LCVs — and enumerating it puts KAWASAKI and a HARLEY-DAVIDSON model list in a car-parts brand picker.** The XSD splits the union into `'V'` Passenger Car, `'L'` LCV and `'B'` Motorcycle. The selector's three `getLinkageTargets` reads go through one constant, `SELECTABLE_VEHICLES` in `vehicles.tecdoc.ts`, set to `LinkageTargetType.CarAndLcv`; widening the shop to motorcycles is that line and nothing else. All three steps must share it — a make list narrower than the model-series list behind it strands a visitor on a make whose series are all bikes.

- **`'VL'` and not `'V'`, because `'V'` deletes the vans.** Measured: MERCEDES-BENZ goes from 39 van series to zero, losing Sprinter and Vito outright, and FORD from 43 to the two Transit Connect/Courier minivans. Adding `'L'` back costs 29 makes that are LCV-only (IVECO, RENAULT TRUCKS) and restores none of the motorcycle-only ones. 466 makes → 286.
- **It filters *variants*, not just makes**, which is what makes it a real scope rather than a make blocklist: KTM keeps its 2 X-Bow series and drops 38 bike series, TRIUMPH keeps 35 car series (Spitfire, TR 6, Herald) and drops 21 bike series, KAWASAKI leaves entirely. A make that builds both stays, showing only its cars.
- **`getLinkageTargets` concatenates these codes and `getArticles` refuses to.** `'VL'` and `'LV'` both answer the union — 286 makes against 257 for `'V'` and 92 for `'L'`, so it is genuinely a union and not an ignored parameter — and `'VLB'` answers all 466 that `'P'` does. The same value sent to `getArticles` is refused `400 Field 'linkingTargetType' has an invalid value:VL`. An unrecognised letter is refused by both, so a typo fails loudly; a recognised wrong one is accepted in silence.
- **Every per-vehicle `getArticles` read stays on `'P'`, and must.** Those pair the type with a `linkageTargetId` and TecDoc checks the pair: a car id answers 772 assembly-group nodes under `'V'` and a van id 656 under `'L'`, but swap them and the *id* is rejected (`400 Field 'linkageTargetId' has an invalid value`). Since the selector now yields both kinds of id and `getArticles` takes one letter only, `'P'` is the only code that accepts either. This is why `getAssemblyGroupTree`, the category listing and the search were left alone — it is not an oversight to tidy up.

`scripts/linkage-target-type-probe.mjs` is the measurement.

#### Vehicle makes: no logo exists, and popularity costs a second call

**TecDoc files no logo for a vehicle manufacturer, and there is nowhere to fetch one from.** `LinkageTargetMfrFacetCount` is `{id, name, linkageTargetType, count}`, `manufacturers2Record` is `{manuId, manuName, favorFlag, linkingTargetTypes}`, and `includeDataSupplierLogo` is on the `getBrands` request alone. Reaching for the parts-brand logos we already cache does not work either: they are *data suppliers* in a different id space, and matching by name was measured at 3 hits over 466 makes — BUGATTI, AMC and TESLA, each a coincidental supplier rather than a car badge. So make logos are ours to ship, as files under `apps/web/public/vehicle-makes/` registered by `mfrId` in `vehicle-make-mark.ts`; an unregistered make renders a wordmark. The manifest is explicit rather than derived from the filename so a missing asset cannot cost a 404 per card, and its spec fails if an entry names a file that is not there. Several `mfrId`s may name one file: Ford's regional arms wear the blue oval and Renault Trucks the Renault lozenge, which is what the wordmark crop leaves anyway.

**The bundled logos are the real badges, fetched by `scripts/fetch-make-photos.mjs` from four sources: 229 of the 286 selectable makes and all 35 popular ones, 228 files for 2.0 MB.** This replaced a Simple Icons set that covered 51 makes as one-colour silhouettes and could not cover Mercedes-Benz at all. Seven things about the set decide how the UI and the script have to behave:

- **The card is white and the badge sits directly on it.** These are photographic marks drawn for white — many are chrome or gradient — so the grey tile they used to sit on is gone, and so is the card's grey hover fill, which would otherwise put its own colour behind every transparent badge on the one interaction that draws attention to it. 28 badges are opaque on white rather than transparent, because their source was a JPEG; that is invisible on a white card, which is *why* the card being white is load-bearing rather than cosmetic. Adding a dark theme means revisiting these 28 first.
- **Matching by name is safe against the dataset and was not before, because the collision was cross-domain.** Simple Icons indexes every kind of company, so PROTON matched ProtonMail, LUCID Lucidchart and SAMSUNG the electronics arm. This dataset holds car manufacturers and nothing else, so those three now resolve to Proton Holdings, Lucid Motors and Renault Samsung Motors, and all 160 exact matches were read off against each entry's `source` URL before the match was allowed to run unattended. **Fuzzy matching is still unusable** — measured, it offered Ford for BEDFORD, Mini for MINELLI, W Motors for SWM MOTORS and International Harvester for IZH — so anything short of an exact match goes in the hand-verified `MAKE_SLUG_ALIASES`. The property that makes this safe is the index's scope, not the matching, which is why the second source below is keyed on an id instead.
- **A lockup is cropped to its emblem, and "take the first band of ink" is not the rule.** The card prints the make name under the mark, so a wordmark in the tile says it twice; but plenty of badges are *drawn* with horizontal gaps, and cropping those to the first band beheads them. The first band's share of the artwork's height separates the two cleanly with nothing in between: real lockups run 0.61–0.82, while Nissan (three bands: arc, wordmark, arc), Triumph, TVR (twelve bands) and Polestar run 0.06–0.49. Chrysler and Maybach invert the layout — wordmark over emblem — so their first band is the caption at 0.26 and 0.19 and both are kept whole.
- **A named Commons file is the third source, for marques whose Wikidata item has no `P154` — the entity-keyed lookup cannot reach those at all.** 13 makes, among them KG MOBILITY (whose item still files SsangYong's mark), TRABANT, JAECOO, ORA, MOBILIZE, YUGO and E.GO. **Each was accepted on what uses it, not on what it is called**: `globalusage` had to show the file in use as the logo on the marque's own Wikipedia article. That check is the whole safeguard, and it rejects convincing candidates — Wolseley's two Commons wordmarks belong to the plumbing merchant, and the AEOLUS candidate is used on an article about football shirts. Passing it is still not sufficient: FARIZON AUTO's file is used on `Farizon_Auto` and is a badge photographed on grey, refused by the opaque-panel guard. A filename is less stable than a Q-id, which is why this is the last resort rather than the first — a rename fails the make loudly instead of silently swapping its badge.
- **Wikidata is the second source, and it is keyed on the entity rather than the name.** The car-logos-dataset has no entry for 116 makes; `P154` on the marque's Wikidata item names its logo on Wikimedia Commons, and `MAKE_WIKIDATA_ENTITIES` maps 30 of those makes to a Q-id — PIAGGIO, DR, AUTO UNION, MOSKVICH, NSU, BEDFORD, TOFAS and the recent Chinese EV brands among them. **Searching Wikidata by name is the Simple Icons failure on a far larger index**: it answers DR with the Danish state broadcaster, INEOS with the chemicals company and MEGA with the file host. So every id was found with a class-constrained query (`P31/P279*` under automobile manufacturer, or an automotive brand) and then read against the item's own label and description, which is why the map stores `Q474988` and the run prints "DR Automobiles Groupe · Italian automobile company" beside it. Commons rasterises an SVG on request (`Special:FilePath?width=512`), so the pipeline still only ever sees PNG. Three classes of candidate were looked at and rejected, and the reasons are in the map's comment: a `P154` that is a *photograph* of a badge on bodywork (GLAS, RELIANT, WOLSELEY), one that is another brand's logo (Wikidata still has SsangYong's mark on the renamed KG Mobility), and one mark shared by two makes TecDoc lists separately (Steyr-Puch). The photograph case is caught by measurement rather than by eye — `isPhotograph` refuses an image with neither alpha nor a flat background to crop against, which is how WOLSELEY was stopped after its thumbnail had passed review.
- **A make with no badge is one whose name cannot be resolved to a logo safely, not one whose logo nobody filed** — and the distinction decides what a fourth source has to do. Measured over the 73 that remained after Commons: 62 have an English Wikipedia article and 60 have a Commons file naming them, so raw availability is high and *every automatic* route to it is poisoned by the same ambiguity. A Commons search offers the Wiktionary logo for MEGA, an antelope for ADDAX, a cola for CAVAN, Intel for EVO and the Pink Panther for PANTHER; worse are the near-misses that look right, where the answer is the *parent* (Deutsche Post for STREETSCOOTER, DR for SPORTEQUIPE) or a sibling marque (Riley for WOLSELEY, Kaiyi for JAECOO). Wikipedia's own infobox is no safer — it resolves BEIJING to the **city** and SPORTEQUIPE to DR by redirect.
- **A logo index is the fourth source, and it is the only one whose provenance is a judgement rather than a property of the data.** `MAKE_INDEXED_LOGOS` holds 16 marks read off image search and reviewed by eye. The first three sources are safe by construction — the dataset indexes car makers only, a Q-id names an entity, a Commons file is checked against what uses it — and an index offers none of that, so two conditions stand in for it: **the mark carries the make's own name as legible type**, which is what rules out the same-named company an image search actually returns (Hero MotoCorp for M-HERO, a Croatian music channel for CMC, the parking operator Indigo for INDIGO, a band for SILENCE, Peruvian robotics for FAAM), and the index files it as a motor marque, which its own filename records. An emblem carrying no name was taken only where a second index agreed: VOYAH, DENZA and M-HERO are on carlogos.org too. Rejected on identity: STEYR (an arms maker, Magna Steyr and Steyr Automotive all answer to it), BEIJING and CMC (their indexed marks are BAW's and a broadcaster's), RANGER, PANTHER, EVO and FAAM. **The dominant result is noise rather than a wrong logo** — "all car brands" collage pages rank for any marque name and were 62% of what came back, cut by counting distinct hues, which is why this source is reviewed by hand and cannot be re-run unattended. ELARIS is the one entry rejected on the image alone: gold on an opaque dark-green panel, refused by the tinted-background guard.
- **The fallback is a permanent state, so it is a wordmark and not a placeholder.** 57 selectable makes have no badge — 279 of the catalogue's 34,977 vehicles (0.8%), the largest with 27. `MakeWordmark` sets those makes' own names as type. It replaced two initials on a striped grey tile, which **collided for alphabetical neighbours** — FEIDI, FENGON and FEST are three identical "FE" tiles in a row — and read as a failed image beside the real badges. The wordmark is not a stand-in for a logo: at least 64 of the bundled badges *are* the make's name set as type (BEDFORD, TOFAŞ, IRMSCHER, BAW, and now CENNTRO and SPORTEQUIPE), so it renders as one more of those. Three details it depends on: the size is in `cqw` against the tile, because the grid is 2, 3 or 4 columns across the breakpoints and one fixed size fits none of them; it is capped by the longest word *and* by the line count, so neither a long name nor a stacked one overruns; and a name of 8 characters or fewer is never split, or B-ON and ICH-X become a stack of stubs. The mark stays `aria-hidden` because the card prints the name below it anyway — without that, every fallback card reads its name twice. Trademark law is unchanged by either source: these are the owners' marks used nominatively, exactly as before.

**`next/image` needs `unoptimized` for these.** The script writes each badge as WebP at 256px, which is the size the tile renders at 2x, so a transform would bill a request per make to hand back what it was given.

**`getManufacturers2` is the only source of "popular", and it is a second call.** The facet that gives the make list carries no such signal; `favouredList: 1` narrows `getManufacturers2` to the favoured makes alone — 35 of the 466 it otherwise returns — so nothing is filtered client-side. Measured live: the call is answered without `provider`, all 35 `manuId`s are present in the scoped facet, and every name matches its spelling for the same id, so the join needs no reconciliation. **`linkingTargetType` is required** (omitting it is refused `400 Field 'linkingTargetType' must be not null`) and this is a *legacy* function, so its letter is a `LinkageFunctionTargetType` and not the `LinkageTargetType` the facet call sends — they collide on `'P'` and disagree on what it means, which is the whole point of the call (below).

**Do not replace that call by ranking the facet's own vehicle count — what the two disagree about is editorial judgement.** Against the `'VL'` facet they agree exactly to rank 21, so a short popular section looks identical either way and the second call reads like dead weight. The split is in the tail: TecDoc favours SMART (88 vehicles, rank 52), LADA (134), DAIHATSU (138), ISUZU, DAEWOO and CHRYSLER over the higher-count IVECO (316), LANCIA (328), LAND ROVER (323), SUBARU, DACIA and ALPINA (183) a count-only cut would promote. That is a claim about what a shopper looks for rather than about how much TecDoc catalogues, and it is not reproducible from the facet. All 35 favoured makes fall inside `'VL'`, so narrowing the scope costs the popular section nothing. `scripts/make-popularity-compare.mjs` is the measurement, and takes the scope as an argument.

Note that this argument used to rest on motorcycles — ranked by count, `'P'` put KAWASAKI, YAMAHA and HARLEY-DAVIDSON at positions 17–19, none of them favoured. `'VL'` removes them at source, so that defence is gone and the editorial one is what remains.

**There is a second source for the same 35 makes, and it is `getLinkageTargets` itself.** `filterMode: 'preferred'` — the preferred vehicle filter (VFF) — is answered `200` on our account and narrows the make facet to **exactly the 35 ids `favouredList: 1` returns**, measured as a set comparison, at 2.3 KB against 2.5 KB. So the legacy call and its `LinkageFunctionTargetType` letter trap could be retired for a flag on a function the selector already uses. It has not been, for two reasons worth knowing before anyone does it: a VFF is configured per account while `favouredList` is TecDoc's own editorial curation, so today's agreement is not a guarantee; and `filterMode` narrows *vehicles* as well as makes (VW 205 series → 143, 2,333 vehicles → 1,757), so it is only usable as a `perPage: 0` read for the id set and never on the make list itself. Settle the semantics with TecAlliance before trading one for the other.

**Neither read may fail soft.** `VehiclesService` issues both (`Promise.all`), merges them and caches the result for a week, so swallowing a refused popularity read would pin a flagless list — no popular section at all — for seven days on one bad response. Letting it throw caches nothing and costs the next request a retry.

**The selector's package splits four ways, and the split is what keeps each piece testable on its own.** `VehiclesTecDoc` is one TecDoc call per method and nothing else — it does not fan out, merge or order; `vehicles.mapper.ts` holds each call's response envelope beside the function that reads it, so "TecDoc omits a collection rather than sending an empty one" is handled in one place per call; `manufacturer-ordering.ts` is the pure merge-and-order rule; `VehiclesService` owns the two-call fan-out, the merge and every cache key. Putting the fan-out back on the TecDoc class is the tempting shortcut — it is one method instead of two — and it costs the ability to state the popularity read's failure rule where the caching that makes it matter actually lives.

**The make list has to be sorted, and TecDoc's own order is the trap.** The facet arrives in ascending `mfrId`, which reads as the alphabet for the first forty entries only, because TecDoc handed out its earliest ids alphabetically and has appended every make added since — the head has `AUTO UNION` before `AUDI` and the tail is `MOBILIZE`, `TIGER`, `FIREFLY`, `EXLANTIX`, `AION`. `orderManufacturers` puts the popular makes first by vehicle count and the rest alphabetically, so a consumer that ignores `isPopular` still gets a sensible order. The web renders those two runs under sticky `ПОПУЛЯРНИ` and `A–Z` markers, pinned because the alphabetical run is 251 makes deep and a visitor part-way down it otherwise has nothing on screen saying which half they are in. A search collapses both into one ungrouped grid, since a query matching a single popular make would leave a heading over one card and an empty section beneath. The probes behind all of the above are `scripts/make-logo-source-probe.mjs` and `scripts/make-favoured-probe.mjs`.

#### The model step: the years, and why there are no thumbnails

**A model series name is a factory code, so what tells two rows apart is the years it was built.** AUDI files 133 series and MERCEDES-BENZ 248, several differing only in the body — "80 B4 Седан (8C2)" beside "80 B4 Avant (8C5)". `scripts/model-series-probe.mjs` is the measurement behind everything here.

**The years are on the facet already, under a second spelling of the same field.** `vehicleModelSeriesFacets.counts[]` carries `beginYearMonth` and `endYearMonth` beside each `{id, name}`, with no include flag of its own — so `ModelSeriesDto.yearFrom` / `yearTo` cost nothing beyond reading them. Two things to know before touching `mapModelSeries`:

- **The facet files the date as a `YYYYMM` integer while every linkage target spells the same field as a `YYYY-MM` string.** A facet count arrives as `{"id":4,"name":"123 купе (C123)","beginYearMonth":197703,"endYearMonth":198512,"count":6}`, and a series target as `"beginYearMonth": "1991-09"`. The field name is identical in both, so nothing about the response says which spelling is in hand — this is why `vehicles.mapper.ts` has two year readers (`yearOf` and `yearOfCompactYearMonth`) rather than one that sniffs the value.
- **`endYearMonth` is omitted for a series still in production, and `beginYearMonth` never is.** Measured over 3,573 series across the 30 largest makes: every series carries a start, 945 of them (26%) carry no end. So `yearTo` is nullable and `yearFrom` is not, and `formatYearRange` renders the open end as `2024+`.

**The series window is wider than any one engine's, so the engine step keeps its own.** Measured on C-CLASS (W205), series 11851: the series runs `201307`–`202302` over 44 variants, while its C 200 runs 2013-12–2018-08 and its C 180 2014-03–2021-03 — no single variant spans the series. Both steps render `formatYearRange`, over `ModelSeriesDto` on the model list and `VehicleVariantDto` on the engine list; printing the series' window beside an engine would tell a visitor a car was sold with that engine in years it was not built. Note also that the body styles are separate series rather than one W205 — T-Model (S205), купе (C205) and кабриолет (A205) each carry their own window — which is what the model list's years are there to tell apart.

##### Both lists are ordered by us, and only one of them could be ordered by TecDoc

**Every step of the selector arrives in ascending internal id, which is the same trap the make list has.** The series facet opens AUDI on `80 B4 Седан` (1991), `80 B4 Avant` (1991), `100 C2 Седан` (1976), `100 C3 Седан` (1982), `80 B1 Седан` (1972) — ids 1, 6, 10, 13, 14 — and the variant rows come back in ascending `linkageTargetId`. Neither is the alphabet and neither is chronological, so `orderModelSeries` and `orderVehicleVariants` in `vehicle-ordering.ts` sort both by name.

- **`getLinkageTargets` does take a sort, and it is refused loudly when wrong.** `sort` is a `{field, direction}` pair; the XSD annotation lists `score`, `linkageTargetId`, `description`, `mfrName`, `beginYearMonth`, `endYearMonth`, `bodyStyle`, `horsePowerFrom`, `kiloWattsFrom`, `cylinders`, `capacityCC`, `capacityLiters`, `tonnage`, `axleConfiguration`, `axleStyle`, `axleType`, `axleLoadToKg` and `salesDescription`. An unlisted field is refused `400 Invalid Sort Field: '…'`, so a typo cannot pass silently.
- **It sorts target rows and not facets, and the difference is silent.** Sending `sort` with `includeVehicleModelSeriesFacets` is answered `200` with the facet in exactly its unsorted order — measured, byte-for-byte the same id sequence. So there is no server-side way to order the model step, and an attempt to add one looks like it succeeded. The engine step is the opposite: `description`, `beginYearMonth` and `kiloWattsFrom` all genuinely reorder the variant rows.
- **The engine step could use it and deliberately does not.** The whole variant list is read at `perPage: 100` and cached for a day, so a sort applied upstream is baked into that entry — changing the order would mean waiting out the TTL, and offering a second order would mean a second entry. This is the rule the article lists already follow: a set we hold in full is ordered by our own comparator, because a second source for one order is a second answer to it.
- **Both are sorted outside their cache entry.** The comparator is a pure function of the list and needs no read, so keeping it outside means a changed order ships on deploy instead of a week (series) or a day (variants) later, and needs no shape bump. Makes are the exception and are ordered inside, because their order depends on the second popularity call and is therefore part of assembling the value.
- **The collator reads numbers as numbers and Bulgarian puts Cyrillic first.** `localeCompare(…, 'bg', { numeric: true })`: without `numeric` the lexical `100 C2` precedes `80 B4`, which breaks every make that names ranges numerically. The locale also orders Cyrillic ahead of Latin, and TecDoc localises only some body words — `Седан` and `купе` but not `Avant` — so one model range lists its translated bodies before its untranslated ones. That is the storefront's own alphabet, not a defect; `'en'` reverses it.
- **A name is not unique, so the tie-break is load-bearing.** TecDoc files two `AMG C 43 4-matic (205.064)` under the W205, at 270 kW from 2016 and 287 kW from 2018. Production start breaks the tie and the id backs it up, so two reads of one series cannot disagree.

##### A thumbnail per model row was built and removed

**It shipped, it worked, and it was cut because it earns nothing the preview sidebar does not already give.** The sidebar shows the car once a model is picked, so a second image in the list is a redundant picture bought with a call per row. What follows is the measurement, kept so the idea is re-argued from numbers rather than rebuilt from scratch.

- **A model series carries no image of its own.** `linkageTargetType: 'S'` answers no `vehicleImages` at all — the XSD scopes that field to Vehicle targets and the live service agrees, 0 of 10 AUDI series targets carrying one. The record is `{linkageTargetId, linkageTargetType, description, mfrId, mfrName, mfrShortName, beginYearMonth, endYearMonth, vehiclesInOperation}` and the field is simply absent. **So a series photo can only be read off one of its vehicles, and there is no bulk read for it** — that is the fact that makes any version of this feature cost one call per row.
- **One record per series would have been enough.** A photo is a property of the series, filed all-or-nothing: over AUDI's 133 series, 101 carry it on their *head* record and only 2 of the remaining 32 carry it deeper. A `perPage: 1` probe costs 2.3 KB against a 20 KB variant list and finds 91–99% of the photos that exist — 2 to 6 series missed a make, except FORD where 13 of 141 file it deeper.
- **Coverage is patchy enough that the placeholder is the point.** By make: VW 20% of series with no photo, AUDI 23%, BMW 29%, MERCEDES-BENZ 35%, FORD 42%, TOYOTA 45%. A list where nearly half the rows are a placeholder is what made the feature not worth its cost.
- **The call volume was never the problem, contrary to first instinct.** The whole catalogue is 5,608 model series across 286 makes, and the shape is extremely skewed — the median make has **4** series, 229 of 286 have 20 or fewer, and only 18 exceed 100. Cached per make for a day, the pathological ceiling was therefore 5,608 metered TecDoc calls a day for every make in the catalogue browsed cold. A single visitor searching at the rate the throttler already permits (30/min, see `ARCHITECTURE.md`) out-consumes that in about three hours. **If this is ever revisited, argue it on whether the picture helps a visitor choose, not on the call count.**
- **Hover-to-load was considered and is the wrong shape.** There is no hover on touch, and the image's only job is to help someone scan a 248-row list — by the time a row is hovered it has already been found, so the fetch arrives after the moment it could have helped. Viewport-driven batching is the coherent version if this returns, and it needs a series-id batch endpoint and per-series cache keys rather than the per-make map that was built.

**The `perPage` ceiling the probe turned up is worth keeping whatever happens to the photos.** `getLinkageTargets` caps `perPage` at **100**, not the 1000 `getArticles` allows — `perPage: 101` is refused `400 Field 'perPage' must be > 0 and <= 100`. Do not size a `getLinkageTargets` pager off the `getArticles` ceiling.

**`getVehicleVariants` reads one page of 100 and does not check for a second, which is measured safe rather than assumed.** Over 2,148 series across the twelve largest makes, none exceeds the cap and the widest is 53 (BMW), so the whole engine list of every series in the catalogue fits one read with about 2× headroom. The response carries `total` and no `maxAllowedPage`, so a series that ever outgrew the cap would silently lose its tail — if the headroom is spent, that is the field to compare the row count against.

**A year narrowing is available on the model step and is not built.** `includeYearFacets` costs 2.1 KB on top of the series facet (19.8 → 21.9 KB) and answers 84 years for VW, and `years: 2015` narrows VW from 205 series and 2,333 vehicles to 53 and 533. Since the years are what tell two factory codes apart, this is the control that argument implies; MERCEDES-BENZ's 248-series list is the case that would earn it.

#### The selector's chrome: a sheet that is full before it is filled

**The preview sheet lists every row from the first paint and dashes the ones it cannot answer yet.** It is the only thing on screen that says what is still to be picked, so rows that appeared as they were answered would both reflow the sidebar on every click and leave the visitor reading their progress off the step tabs alone. `previewSpecs` therefore always emits Година, Двигател, Мощност and KBA код; Обем and Гориво join them only once a variant is picked, because those two are facts about an engine rather than slots waiting for one. An unanswered row prints an em dash, which is why the labels carry no colon — the dash is the value, not a placeholder for one.

**`kbaNumbers` is the one field on the sheet a visitor can check against their own paperwork, and it costs nothing to serve.** `getLinkageTargets` sends it with every vehicle target exactly as it does `vehicleImages`, so there is no include flag and no second call; measured over 227 variants across nine series, 218 carry at least one number, 59 carry two and 10 carry three. Several is normal rather than a data fault — one number per type approval — so the row joins them instead of taking the first, and the value is set in the mono face because it is a code to compare character by character, not a word to read.

**`engineCodes` is the same field as `kbaNumbers` in every respect that matters, and it was served truncated for longer.** `engines[]` rides along on the same read with no flag of its own, and **a third of vehicles are built with more than one engine**: measured over 1,298 variants across the six largest makes, 447 (34%) carry several and one carries seven — a Mercedes E 300 CDI files `OM 642.852` and `OM 642.850`, an E 63 AMG `M 157.980` and `M 157.981`. `mapVehicleVariant` took `engines[0]` and the sheet printed it as `engine`, so a visitor whose block is stamped with the sibling code read a car that was not theirs. The list is now kept whole (`VehicleVariantDto.engineCodes`) and joined wherever it is shown, exactly as the type approvals are. `engines` is optional in the XSD and present on all 1,298 measured, so an absent collection reads as no codes filed rather than as a failure.

**The engine step searches over those codes, and could not before.** A code is never in the description — measured over one series, 0 of its 28 variants carried its own code in the name — so a filter over the name alone answered every code query with an empty list while the placeholder advertised `Търси двигател или код`. `variant-search.ts` matches over the name, the engine codes and the type approvals, stripping both sides to alphanumerics first, because TecDoc spaces and dots a code and a visitor reading theirs off a block has no reason to punctuate it the same way.

**Series and variants are cached for a week and a day, so adding a field to either DTO means flushing Redis before the new field shows up.** A held entry keeps the shape it was written with — the sheet once read `kbaNumbers.join()` on one that had none and took the whole dialog down. Nothing is deployed, so the answer is `redis-cli` and a restart rather than a version in the key; see the pre-launch rule in `CLAUDE.md`.

**The frame behind the mark is white, for the reason the make cards are.** It renders a bundled badge, a TecDoc vehicle photo or a hatched placeholder in one fixed `16/9` slot, and 28 of the badges are opaque on white — a tinted frame would print a visible panel behind each of those. The placeholder's diagonals are the `hatched` utility in `globals.css` rather than an asset, so the empty state costs no request; the same utility fills the thumbnail slots in the model list, which is what makes an unillustrated row read as a pending photo rather than a broken one.

**Both marks travel outside the selector, and only one of them can be saved with the vehicle.** The header pill and the search sidebar's vehicle card showed a generic car glyph in a 36px tile; they now show the make's badge, and the sidebar card also shows the series photo above it. The badge is free to put anywhere — it is a bundled file keyed on `manufacturerId`, which is one of the fields `SelectedVehicle` persists — but it falls back to the car glyph rather than to `MakeMark`'s wordmark, because a wordmark is sized in container units and `STANDARD AUTOMOBILE` resolves to under 5px in a tile that size. **The photo cannot be persisted at all**: its URL is a token minted per response, so a copy saved beside the vehicle in `localStorage` would be dead long before the vehicle was. `useSeriesPhoto` re-reads the variant list for the stored `seriesId` instead, which shares a query key with the selector's own read and is answered from the API's day-long cache. Do not "optimise" that into a field on the store. The card renders nothing when the series files no photo, for the coverage reason above — reserving the space would put an empty box on about a third of cards to spare the rest one early reflow.

**The section headings are full-bleed and opaque, and both halves matter.** `ПОПУЛЯРНИ` and `A–Z` pin to the top of a scroll container that has its own horizontal padding, so the band is pulled out to the container's edges with a negative inline margin and puts its padding back — a heading inset to the card grid reads as a label on the first card rather than a marker for everything under it. It must also be fully opaque: cards pass directly beneath it, and any transparency shows a badge sliding through the text.

**Stepping through make, model and engine is the only way in, because VIN and plate lookup need a licence we do not hold.** Both the hero card and the dialog header offered a mode tab for them, wired to nothing — a control that cannot answer, which is worse than an absent one because it advertises a capability. They are gone, along with the VIN input that sat under the hero's three fields behind an `или` divider. Do not restore any of them as a disabled state or a "coming soon": the blocker is a commercial licence, not unfinished code, so there is no build order in which the stub becomes useful. `vehicle-finder-manual.spec.tsx` guards that neither the input nor the divider comes back.

**The hero's call to action does the step the visitor has not done.** With no vehicle it reads `Избери автомобил` and opens the dialog; only once one is picked does it become the `Към каталога` link. An unconditional link is the tempting simplification — it is one element instead of two — and it spends the card's most prominent control on a destination the nav already offers, from a card whose whole subject is the vehicle. Both states share one class constant, since they differ only in text and element. It branches on persisted state, so it reads through `useHydration` and asks for a vehicle until the store is known; that is also the state the server renders, so the first paint matches.

**The hero's three fields carry the same numbered chips as the dialog's tabs, and the fill differs on purpose.** A step not reached yet is a filled grey chip here and a tinted one in the dialog: the tab strip sits on the beige canvas, which a faint circle reads against, while the card is white, where the same treatment leaves the numeral floating with no chip around it. The two are separate definitions rather than one parameterised component — size and waiting-fill are both surface-specific, which is most of what the markup is. What they do share is the rule: dark for the step to start on, green tick for one answered, and the chip out of the accessibility tree. The hero has no partial state to render (`stepStateOf`): the store holds a whole vehicle or none, because all three names arrive from one pass through the dialog, so its chips are all ticked or all waiting behind step 1.

**A step tab's number becomes a tick, not a second glyph beside one.** The badge is the step's state — grey for a step not yet reachable, dark for the one open, and a green tick for one already answered — so the numeral is what it replaces rather than something a tick is added to, and the tick is what lets a visitor scan for the first unanswered step without reading the labels. The selected value is muted next to its label so the label stays the thing being scanned, and the badge is `aria-hidden`: the tab already names its step in text, and a screen reader announcing "one Марка" reads the ordinal as part of the make.

#### Article identity: an article number is not unique

**A TecDoc article is identified by `(dataSupplierId, articleNumber)`, never by the number alone.** Two data suppliers can and do file the same number for different parts. A number-only `getArticles` lookup returns every one of them and the caller takes whichever the catalogue sorted first — which is a coin toss, not a lookup. This surfaced as an article detail page showing another company's specs and applicable vehicles.

`dataSupplierId` is the brand: it is what `getBrands` is keyed by, what the onboarding guide's catalogue-data table calls `BrandId`, and the only brand axis `getArticles` can filter on. It travels through our own contracts as `brandId` on `ArticleSummaryDto`, `ArticleAutocompleteItemDto` and `BrandDto`.

Rules when adding anything article-scoped:

- **Resolving one specific part** — send `dataSupplierIds: [brandId]` plus `searchMatchType: 'exact'`, and route it through `ArticlesTecDoc.articleLookupPayload`. The public route is `/catalog/brands/:brandId/articles/:articleNumber`.
- **Cache keys, query keys and React list keys** carry both halves. A number-only key serves one brand's part to everyone asking for the other.
- **Every link to a part** goes through `articleDetailHref(brandId, articleNumber)` in `apps/web/src/lib/catalog/article-href.ts`.
- **There is no exception, substitutes included.** Which parts replace a part is a property of that part, not of its number, so two suppliers filing one number have different replacements — see the next section.

**Stock is matched on the same identity, in the `WHERE` clause.** `public.autoparts` and `public.supplier_stock` both carry `tecdoc_supplier_id` next to `tecdoc_number` and both are indexed on the pair, so the repositories query `WHERE tecdoc_number = … AND tecdoc_supplier_id = …` and the database does the narrowing — there is no post-filter in TypeScript to keep in sync. The batch read joins the wanted pairs in as two parallel arrays (`unnest($1::text[], $2::text[])`), which plans as one index lookup per pair: 1.7 ms for 500 pairs. Number-only matching was mispricing — 13,596 numbers in `supplier_stock` are filed by more than one supplier, and 23% of measured number-only matches attributed stock to the wrong brand — so `InventoryService.getAvailability` takes `ArticleIdentityDto[]` and answers a map keyed by `articleIdentityKey(brandId, articleNumber)`, and `GET /catalog/articles-availability?articles=268:WL6340` carries both halves on the wire. A line whose `tecdoc_supplier_id` is null, an internal OE code, or a zero-padded internal code simply does not match, which also leaves original parts unreachable — they are a separate relation, see `TODO(inventory-oe-parts)`.

#### An article's place in the category tree

**An article's breadcrumb comes off the detail read itself, at the cost of a facet over one row.** `getArticleDetails` adds `assemblyGroupFacetOptions` to the same `getArticles` lookup that fetches the gallery, criteria and OE numbers, and `assemblyGroupPathsOf` walks the returned `parentNodeId` links into root-to-leaf trails. Measured on MAHLE `OX 389/1D`: 7 nodes for +986 bytes on a 9,457-byte response, no second call. `scripts/article-category-probe.mjs` is the measurement.

- **The tree has to be named, and a facet that names none answers with nothing.** `{ enabled: true }` alone returns 0 nodes and +46 bytes — the empty block. TecDoc infers the tree from a linkage where there is one, and a lookup by number carries none, so this call always sends `CATALOGUE_WIDE_TREES`. It is the same `'PU'` the catalogue-wide search sends, and for the same reason: universal parts are filed in the other tree. (On this article `'P'` and `'PU'` happen to answer identically, since an oil filter is a passenger-car part.)
- **One article has several trails, and picking between them is ours to do.** `OX 389/1D` comes back as `филтър › маслен филтър`, `двигател › смазване › маслен филтър` **and** `части за сервиз/ инспекция/ обслужване › Периодична подмяна` — the same flattening of orthogonal axes the category options section describes, seen from one article instead of a result set. Measured over 20 articles sampled across oil filters, air filters, brake discs, pad-wear sensors and handbrake switches: 12 carry three trails and 8 carry one, all 44 chains complete to a root, none missing the facet. So `ArticleCatalogDetailDto.categoryPaths` is a list of trails and never one trail, and the API deliberately picks none of them — that choice belongs to the client, which knows which one the visitor drilled and is the only party that does.
- **The web's rule is the drilled trail first, then the shortest.** `selectArticleCategoryPath` prefers a trail containing the `categoryId` the link carried; failing that it takes the shortest, which over every article measured is the one saying what the part *is* rather than where it sits on the car or why it is replaced (`филтър › маслен филтър` for the oil filter, `спирачна уредба › Индикатор за износване` for the pad-wear sensor). The label tie-break is load-bearing rather than cosmetic: the detail page is cached, so a trail chosen by TecDoc's arrival order would outlive the read that chose it.
- **`categoryId` on the article URL is what carries the drilled trail**, written by `articleDetailHref` and read by nothing else. A surface with no category of its own — an autocomplete row, a substitute of another part — leaves it off and the fallback answers.
- **The `assemblyGroupNodeId` on `genericArticles[]` is a different id space, and it is free, which is the trap.** `includeGenericArticles` already carries `{ assemblyGroupNodeId: 72, assemblyGroupName: 'смазване' }` on `OX 389/1D`, so it looks like the trail's leaf for nothing. It is a legacy id: the facet calls that same category `100245`, filtering by `100245` matches 147,799 articles, and filtering by `72` is refused `400 Field 'assemblyGroupNodeId' has an invalid value:72`. Read the free field for display if you must; never link or filter by it.
- **A category can be read on its own, which is what a clickable crumb will need.** `assemblyGroupNodeIds: [100259]` with no `searchQuery` is answered `200` with 39,571 oil filters (`maxAllowedPage` 5,000), and the root `100005` with 284,347. So the catalogue supports a category browse today; what does not is our own `/search`, whose `q` is `@IsNotEmpty()`. Until there is a page for it, the category crumbs render as text and only `Начало` links — see `buildArticleBreadcrumbs`.

#### Cross-references: candidates first, detail per page

**Which parts replace a part is read from the cross-reference index, in two phases: a cheap search for the whole candidate set, then a rendered-row read for the page a visitor reached.** `docs/CROSS-REFERENCES.md` is the design document — it carries the live measurements every number below comes from, and the alternatives that were rejected. The code is one package, `catalog/articles/cross-references/`, reached through its barrel: `cross-references.tecdoc.ts` (the candidate search) and `candidate-set.ts` (the pure filtering and provenance rules). The two phases the search shares with it — the ordering, the row hydration and the paging — live in `catalog/articles/article-list/`, described below.

**Phase 1 — the candidate set.** One `getArticles` with `searchType: 3` (Comparable Number) on the part's *own* number, narrowed by `genericArticleIds` to the type of part it is, asking only for `includeGenericArticles`, `includeComparableNumbers` and `includeMisc`. A candidate costs under a kilobyte, so the complete set arrives in one call at `perPage: 1000` — TecDoc's own maximum, against a measured median of 99 and a widest of 354 (341 KB) over 418 parts — and is cached whole. There is no paging loop, deliberately: a second page could only carry a set wider than the ceiling, so `readCandidates` warns on a truncated set instead of paging for a case three times wider than any in the data.

**Phase 2 — the rendered page.** The `legacyArticleId` each candidate carries feeds back into `getArticles` for the description, images and criteria a row shows — 25 rows cost 217–251 KB, which is why only the page a visitor reached is paid for. This half is `ArticleRowsCache` (see the article-list section), shared with the search. The includes are exactly what `mapArticleSummary` reads and nothing else: `includeArticleText` and `includeOEMNumbers` were requested here until measurement showed the mapper reads neither, and dropping them saved 32–60% with the mapped rows byte-identical. Never `includeAll` either: `pdfs`, `links`, `linkages`, `partsList`, `accessoryList`, `gtins` and `prices` all ride along in it and none is rendered.

A bare comparable-number search *is* unusable, and two things in the same response fix it — neither of which an earlier attempt used:

- **`genericArticleIds` narrows to the part's own type**, server-side. A.B.S. `16100`: 269 candidates down to 58 brake discs.
- **Each row reports whose number it matched**, in `comparableNumbers[].dataSupplierId` — the same id space as our `brandId`. `keepCandidatesCiting` keeps only the rows citing *this* brand's number, which is what turns a loose number match into equivalence. Do **not** use `searchQueryMatches` for this: it names the brand by `mfrId`, an unrelated id space (see the warning in `article-mapper.ts`).

What follows:

- **Both halves of the identity travel.** The routes are `/catalog/brands/:brandId/articles/:articleNumber/substitutes` and `.../part-numbers`; the cache keys (`tecdoc:crossrefs:…`, `crossrefs:order:…`, `tecdoc:article-row:…`), the TanStack query key and the React list keys all carry brand *and* number.
- **An empty list is a legitimate answer.** A part TecDoc files no generic article for is not searched at all, and a candidate set the provenance filter empties stays empty — a wrong substitute is a part a mechanic fits to the wrong car.
- **The whole set is ordered by what we can ship**, then paged: in stock first, then fastest delivery band and lowest price, then supply status, and finally `(brandName, articleNumber)` so paging is deterministic. This is why the set is read whole — a sort on stock is only meaningful if it sees every candidate. `orderArticles` in `catalog/articles/article-list/article-ordering.ts` is the one definition of that rule, structural over `OrderableArticle` so any list surface ranks rows the same way; a second definition is a second answer to "which part do we show first". Cross-references take the default sort and offer no choice — the visitor came for what replaces a part, not for an alphabet.
- **That order is pinned for five minutes, and this section needs it more than the search does.** It pages by appending: re-ranked between two clicks of "show more", a row whose last unit sold in between drops a place, so the next page appends a row already on screen and silently skips another. `crossrefs:order:<brandId>:<articleNumber>` holds the ranking through `ArticleOrderCache`, which every paged list shares. An order re-ranked after the pin expires can still cross one page boundary — a cursor would be the only complete fix, and it is not worth a contract change for a window measured in minutes.
- **`InventoryService.getAvailabilityForOrdering` is the only fail-soft availability read.** `getAvailability` fails closed everywhere — every buy box, every checkout re-check — and a list that ranks by stock is the one thing an outage must cost its *order* rather than its existence, so it answers null and the ordering falls back to catalogue data. Keeping that in one named method is what stops the exception being swallowed by a try/catch in each new surface.
- **The delivery rank is the band, never `deliveryWorkDays`.** `CENTRAL` and `REGIONAL_1` both file nought working days — our own shelf, and a supplier that ships today if the order beats its cut-off — so on days alone they tie, price decides, and the list interleaves green-badge rows with blue ones. `deliveryBand` in `packages/shared/src/delivery.ts` is the one definition of that band: the web colours the availability dot from it and the API sorts by it, so anything ranking or badging delivery speed reads it from there rather than re-deriving it.
- **One search is the whole answer — there is no second source and no top-up.** A thin list is served thin: how many suppliers cite a brand is a property of TecDoc's data. An OE-number fallback shipped first and was removed, because "which parts fit the same original" is a different relation from "which parts replace this part", and mixing it in below a threshold meant two visitors could see rows selected by different rules. Do not add a second source here without deciding what the list *means*.
- **The substitutes route is paginated and the part-numbers route is uncapped.** `total` counts the whole set, so the section offers every alternative; the chips need only a number and a brand, which the candidate already carries, so that surface pays for no hydration of its own. It also answers with the article's OE numbers, read from the cached article read the cross-reference search already made — see the list-call includes below for why no list response carries them.
- **TecDoc normalises punctuation and spacing on both sides of a number match**, so `895 615 301`, `895615301` and `895-615-301` are one number and one search.
- **Drop the viewed part, on `(dataSupplierId, articleNumber)` and never on the number alone.** The search answers with the part it was given among the rest (60 of 236 sets measured), and matching on the number alone would also drop the *other* supplier's part filed under it — which is a genuine replacement, as the KNECHT/MAHLE `KC 69` pair shows. Nothing else is dropped: there is no dedupe, because no candidate set repeats a pair (0 in 542 sets / 30,830 rows) while 495 of those sets legitimately have one supplier contributing several rows under different numbers.

#### One list pipeline: `catalog/articles/article-list/`

**Every surface that shows a ranked, paged list of articles reads it the same way, and that way lives in one package.** The cross-references and the search both enumerate a whole set of candidates, rank it by what we can ship, cut a page out of it and buy rendered rows for that page alone. Five pieces, reached through the barrel:

- **`article-ordering.ts`** — `orderArticles`, the single definition of "which part do we show first", structural over `OrderableArticle`. It is also the one place a `SearchSort` becomes a comparator, so two surfaces asked for one order cannot answer it differently.
- **`article-order.cache.ts`** — `ArticleOrderCache.ordered(key, candidates, sort)`: ranks a whole set against one batched stock read and pins the resulting order for `ARTICLE_ORDER_TTL` (five minutes) under the caller's key. `sort` defaults to availability, and the caller's key must distinguish one from another or two sorts share a pin. Every paged surface goes through it, because "which part do we show first" and "how long does that answer hold" are one decision — a list answering the first without the second re-ranks under the visitor mid-page. It is also the only caller of `getAvailabilityForOrdering`, which keeps the one fail-soft stock read in one place.
- **`stock-scope-selection.ts`** — `selectStockScope`, the narrowing and counting of a ranked set by stock origin. Pure, because it needs no read of its own: the pinned order records which origins could ship each article, so the answer is already in hand. See "Narrowing a list by stock origin" below for why a second read is the wrong shape here.
- **`article-rows.tecdoc.ts` / `article-rows.cache.ts`** — the hydration read, `legacyArticleIds` → `ArticleSummaryDto`, cached per row under `tecdoc:article-row:…`. Per row rather than per page, so two surfaces asking for the same part and any two pages that overlap after a re-rank share the entry. It asks for a `HydratableArticle` — an identity and the id to fetch it by — and nothing more, which is what keeps a stored ordering to identities plus the two origin bits.
- **`article-page.ts`** — `pageOf`, the slice.

**Narrowing a list by stock origin costs no read, and must not start costing one.** `StockScope` (`packages/shared/src/stock-scope.ts`) splits stock into `central` — our own shelf — and `external`, everything a supplier holds; `stockScopesOf` derives both from the warehouses behind one article. Ranking already resolves those warehouses for every candidate, so `ArticleOrderCache` records the origins alongside the order and `selectStockScope` reads counts and filters straight off them. Four things follow:

- **Reading stock again for the counts is the expensive mistake here.** Measured on `InventoryService.getAvailability` over real identities: 9.5 ms for 100 articles, 26 ms for 500, 70 ms for 1,000 — and two thirds of that is synchronous offer selection and delivery projection per article, which blocks every other request in the process. It also lands on *warm* requests, where a pinned order previously needed no stock read at all. The 1.7 ms in the identity section above is the SQL plan alone; do not quote it as the cost of the call.
- **The counts belong to the same snapshot as the order, not a fresher one.** Row *positions* come from a pin up to five minutes old, so counts from a live read would describe a set ranked differently from the one on screen. Pairing them with the order is the more consistent answer, not the staler one.
- **The origins are predicates, not a partition.** A part we stock that a supplier also stocks is in both, so the counts overlap and never sum to the total. Anything rendering them as segments of a whole shows a number that does not add up.
- **Missing origins mean "unknown"; an empty list means "nowhere".** A failed stock read leaves `stockScopes` absent for the whole set, which `selectStockScope` answers with null counts — the signal a client drops the control on. An entry pinned before this shipped reads the same way, so the control is simply absent for the few minutes it takes those to expire.

**A pinned order is per surface but never per page.** The key names the whole set — `search:order:…` for a search, `crossrefs:order:<brandId>:<articleNumber>` for a part's substitutes — so one entry answers every page. A page number in that key would defeat the point of pinning.

**A candidate is not an `ArticleSummaryDto`, deliberately.** `ArticleCandidate` (in `tecdoc/article-mapper.ts`, mapped by `mapArticleCandidate`) carries the identity, the description, the supply status and the `legacyArticleIds` — under a kilobyte, against roughly ten times that hydrated. That ratio is what makes reading a set of a thousand whole affordable, and it holds only while the candidate stays thin: nothing on it may come from `includeImages`, `includeArticleCriteria` or `includeOEMNumbers`.

#### Search: enumerate the set, then rank what can be ranked

**A search reads its match set whole before it reads a page of it, and how wide that set is decides which order the visitor gets.** `SEARCH_SORTABLE_LIMIT` (1000, TecDoc's own `perPage` ceiling) is the boundary, and `search/search-enumeration.ts` is the one place the tier is decided:

- **At or under the limit** — the set arrives as candidates in one `enumerate` call, `orderArticles` ranks all of it against one batched stock read, `pageOf` cuts the page and `ArticleRowsCache` hydrates that page. Every sort is available.
- **Over it** — the set cannot be ranked, so it is served from `readRowsPage`, a plain page read, in whichever order TecDoc can apply itself. The response says `isRankable: false`, and the web turns that into a prompt to narrow (`SearchWideSetNotice`).

What follows from that split:

- **The request and the response share one sort vocabulary**, `SearchSort` in `packages/shared/src/dto/search/search-sort.ts`, of which `SearchOrdering` is an alias. A request value the response could not express would be a promise with no way to say it was not kept: `?sort=price_asc` over a set too wide to rank is answered `ordering: 'catalogue'`, never `price_asc`. `requiresRankedSet` is the one definition of which sorts need the whole set, shared so the web can build its menu without restating the API's tiering rule, and `sortForUnrankableSet` is the one definition of what each falls back to.
- **`ordering` and `isRankable` on `SearchResponseDto` are both required, and they are not interchangeable.** `ordering` is the order actually applied; `isRankable` is whether the set was enumerated. Inferring the tier from the ordering worked only while `catalogue` meant "too wide" — a visitor may now *choose* it over fifty results, and reading that as a wide set would hide the stock filter and raise the narrowing prompt on a set that is already narrow.
- **The enumeration is page-free, and so is its cache key.** `searchSetCacheKey` carries the query, the scope and the filters and *not* the page, so one entry answers every page of a search. `searchPageCacheKey` is the fallback's, and is the only search key a page number belongs in.
- **The sort belongs in the order key and the page key, and never in the set key.** The same articles match whichever order they are read in, so keying the enumeration on it would re-fetch a thousand candidates to hand back rows already in hand. The pinned *ranking* is the opposite case: sharing one entry across sorts would page on through the previous ranking, so switching the control would leave the list unmoved with nothing thrown and nothing logged. The fallback's page key needs it because TecDoc does that sorting inside the page read.
- **The saved vehicle never scopes a search on its own.** It is a header preference, not a standing filter on everything typed after it: a visitor who picked a car once does not remember it three searches later, and a silently narrowed result set reads as a catalogue missing half its parts. So `newSearch` takes no vehicle and the search box sends none — `?vehicleId=` is written only by the results page itself, from `SearchVehicleFilter` in the sidebar or the wide-set notice, where the narrowing is named, counted and reversible. It is counted by `isNarrowedSearch` rather than `hasActiveFilters`, so a scoped search matching nothing keeps the sidebar that can widen it again instead of landing on the dead-end empty state. None of this reaches the API, where `vehicleId` remains a first-class part of the match-set identity and its cache keys.
- **The stock filter is the one narrowing no search cache key carries.** `stock` is applied after ranking, over a set TecDoc knew nothing about, so all three states of the control share one enumeration and one pinned ranking. Putting it in the keys would re-read the same match set from TecDoc for each and pin three copies of one order — `search-cache-keys.spec.ts` guards this.
- **Stock is read whatever the sort, including the alphabetical ones.** The origins it yields are what the stock filter counts and narrows by, and that control is offered over any order — so `ArticleOrderCache.ordered` reads stock even when the comparator ignores it. This is why a sort costs nothing extra: the read was already happening.
- **A wide set is cached without its candidates.** TecDoc will not count a set without naming articles from it, so they are read and then dropped by `withoutCandidates` before the entry is stored: what is left is the total, the facets and the navigation, which is all the fallback path reads.
- **The dimension facets are ours to shape, and TecDoc will not do any of it.** `search/dimension-facets.ts` owns the whole rule; the raw `criteriaFacets` block is not something to pass through. `includeCriteriaFacetsSorting`, TecDoc's own recommended ordering, is refused on our account (`400 Sorting of criteria facets is not enabled`), so a vehicle-scoped search would not unlock it either — and `CriteriaInfo` carries no sort field to fall back on. Four rules, measured live:
  - **Only `criteriaType` `N` and `K` are offered**, as an allow-list. Type `A` is free text a supplier typed — 3,620 values across 13 criteria on one product type, among them `за OE-номер` with 2,216 and thread sizes filed as `M20x1.5-6H`, `7`, `X`, `0` — and type `V` is always the single placeholder "Данни за автомобила". Type `D` is a date, and it is dropped for a different reason: it appears only under a linkage (criteria `20`/`21`, "година на производство от/до", `isInterval: true`, filed `YYYYMM` and rendered `MM.YYYY`), so it is the build-date window a part is restricted to — a real fact about the article, but one TecDoc has already applied in matching the vehicle. It belongs on the article, not in the sidebar.
  - **Spellings of one value are merged, and this is a correctness fix rather than tidying.** TecDoc files one measurement under several raw values: `ширина [mm]` offered `193` matching 358 articles beside an identical-looking `193` filed as `193,0` matching 12, and 17 of 18 numeric criteria were affected. A measurement merges on its numeric value (decimal comma *and* point both appear in one response), anything else on the rendered label — which is what makes the key-table pair `SA`/`S`, both "комплект", one choice. The merged value keeps every raw spelling in one `|`-joined token, and `parseCriteriaFilters` expands it back to one `criteriaFilters` entry each; `|` appeared in none of 40,698 measured values. This leans on the same property as the multi-select — that TecDoc OR-combines filters sharing a `criteriaId` — which is measured: `форма`=Правоъгълен matched 3,201 and `форма`=кръгъл 1,341, the two together exactly 4,542, while adding a *second* criterion narrowed 3,201 to 3,022. Same id ORs, different ids AND.
  - **Values are ordered here or not at all.** 31 of 33 multi-value numeric criteria arrived unsorted, and the raw values are strings with a decimal comma, so a lexicographic sort puts `100` before `89`. A numeric criterion is a scale and reads ascending whatever the counts; a key table has no inherent order, so the most-matched leads. The label breaks every tie, so one set cannot come back in two orders.
  - **The 60 that reach the wire are capped again on screen, at 12, and the on-screen window is chosen by count exactly as the API's is.** `AttributeValueList` keeps the 12 most-matched values and renders them in the order the API served, which is the same split of concerns as `capValues` (which values are worth offering) and `orderValues` (what order to offer them in). Taking the first 12 in display order is the tempting shortcut and measures much worse, because a measurement's prefix is its low end: over 118 numeric criteria it reached a median 21% of matched articles against 62% for the most-matched 12, and on brake-disc `Кръг на дупките` 3% — 55–69 mm of noise instead of the bolt patterns anyone would click (98, 100, 108, 112, 114.3, 120). Key tables are identical either way (99%), since the API already orders those by count. Reveals of 24 mean 12 → 36 → 60 always reaches the whole set in two clicks, which is why this batch is larger than the brand list's 10 — that list can run to hundreds and leans on its text filter instead. Most criteria never reach either cap (median 6 values over 431 measured); it is the fifth arriving at or near 60 that would otherwise fill the sidebar, where the three criteria open on arrival totalled 98–152 pills. A selection outside the window stays rendered, for the same reason the API keeps it in the payload.
  - **`DIMENSION_VALUE_LIMIT` caps each criterion at 60, keeping the selection** — same rule as the product-type cap, and for the same reason. Uncapped, the criteria block is 95% of the enumeration response (38 KB without it, 796 KB with). The four rules together took one product type from 13,361 values / 591 KB to 1,028 / 52 KB and a leaf category from 29,957 / 1,413 KB to 1,496 / 82 KB. A capped list of points is the control, and a min/max range was considered and rejected: **TecDoc cannot filter by range at all** (`CriteriaFilter` is `{criteriaId, rawValue}` and nothing else), so a range could only be expanded into the discrete values inside it — and `includeCriteriaFacets` is a plain boolean with no way to ask for one criterion, so the full value set always costs the whole criteria block (837 KB on air filters, 1,357 KB on brake discs). Caching the value-to-spelling map an expansion needs adds 80–155 KB per entry, the alternative is a second call per filtered search, and the values carry outliers that would make a slider lie (`височина` runs to 51,916 mm, `центриращ диаметър` to 92,036 mm).
- **Dimensions wait for a selection, and auto-surfacing them on a precise query was measured and dropped.** A match set never narrows to one product type on its own: free text spans hundreds (`филтър` → 213 types), and an exact number fans out over OE, trade and comparable numbers onto kits and service sets as well as the bare part, so it lands on two to six — `OX 389/1D` is 114 articles across 83 brands, 110 an oil filter and 4 a filter kit, which misses the gate by one type. It held in 0 of 48 exact searches sampled across eight product types, and the shapes that did collapse held one or two articles, where no filter can change the result. Where a number search does need an axis, the visitor's is brand, which is already there.
- **A leaf category is a much weaker gate than a single product type, and the numbers say how much.** `hasCoherentDimensions` accepts either, but the leaf "Периодична подмяна" spans 109 criteria against 59 for one product type, because everything serviceable is filed under it. Ordering the criteria stays on the web (`orderedFacets` in `attribute-filters.tsx`); ordering the *values* inside one is the API's, so nothing re-sorts them on arrival.
- **No facet narrows itself, which is what makes the multi-selects work.** TecDoc counts each facet *before* applying that facet's own filter, so a selection never collapses the list it came from: with one brand selected the brand facet still answered all 118 values, and with one dimension value selected that criterion still answered all 15, while the facets a filter legitimately narrows did narrow (the brand filter took product types 107 → 4). Every multi-select depends on this — a facet narrowed by its own selection offers one value and no way to add a second, and the fix would be one extra call per facet. It is measured rather than documented by TecDoc, so re-check it before trusting a *new* facet to behave the same way.
- **The fitting position is a place on a car, and it is read from the key table rather than the label.** Criterion 100 ("страна на монтаж") declares `keyTableNum: 90`, and `getKeyValues({ keyTableId: 90 })` serves that table whole — 804 entries of `{ keyId, keyValue }`, in which 188 of the 189 values seen live carry the label the facet reports. So the facet's `rawValue` is a stable, language-independent id, which is the only reason the web can draw a clickable car: `fitting-position-zones.ts` maps code → `FittingPositionZone` and `FittingPositionDiagram` lays the zones over an outline. Four things to keep true:
 - **Never derive a zone from the label.** They are localised and inflected — `VR` reads "на предната ос отдясно", so a match on "предна ос" misses it on the Bulgarian definite article alone, which is how a first attempt lost the two busiest wheel positions. Alphabetic codes were each checked against their table-90 label; numeric ones were taken only on a strict `N. <axle> [side]` shape, so a substring match could not pull in "предница на автомобила" — the front of the *shell*, not the front axle.
 - **A zone owns a set of codes, not one.** TecDoc files front-left as both `VL` (180k) and `LV` (18k), and again per numbered axle, so a zone that sent only the busier spelling would silently drop the rest. `toggleAttributeGroup` applies or clears the whole set in one step; TecDoc OR-combines them because they share a `criteriaId`, the same property the merged values rest on.
 - **The criterion is a grab-bag, so the chip list stays.** The 32 mapped codes are 84% of measured usage (1,236,807 of 1,464,928 occurrences), and the rest is not placeable on a plan: levels (`U` отдолу, `O` горе), relative positions (`VD` пред оста, `HD` зад моста, `RS` от страната на колелото), and outright non-wheel entries (за цилиндър 1-4, B-колона, багажно пространство). `chipValues` renders exactly what the diagram could not.
 - **Zones are absent, never disabled.** They are derived from the values a search actually offers, because that set is small and varies by product type: DQM alone takes брава на врата from 46 values to 7 and главен фар to 2, and a single article commonly has three. A headlight or mirror offers only `L`/`R`, which is why `left` and `right` are zones in their own right rather than a grid of axle × side — without them the control would render empty for two of the largest categories.
- **Category options are served in TecDoc's own order and `sortNo` is not read** — see the comment on `buildCategoryNavigation` for the measurements. The order that arrives is already alphabetical and stable, so sorting would trade one defined order for another and invent a tree precedence to do it.
- **The product-type facet is capped and the brand facet is not.** TecDoc counts every one of its ~7,600 generic articles a query touches — measured at 7,541 values, 721 KB of a 786 KB cache entry and the same again on the wire, for `q=1` — while `showsProductTypes` only renders that list once the category tree runs out of levels, where the widest measured set was four. `PRODUCT_TYPE_FACET_LIMIT` keeps the 60 most-matched, **plus whatever is selected**: TecDoc counts product types *before* applying its own `genericArticleIds` filter, so this list is where a deep-linked page reads its own heading and breadcrumb, and a cap that drops the selection loses both. Brands are bounded by the number of data suppliers (525 at the widest, 32 KB) and the sidebar sorts them alphabetically behind a search box, so capping them by count would silently remove brands from the alphabet and the search alike.
- **The category facet asks for neither the whole tree nor a depth, and both omissions are measured.** `includeCompleteTree` reads as though a facet filtered to a node were anchored there with no way back up — the trail the breadcrumb walks — and it is not: such a facet answers with the node, its children *and* its complete ancestor chain regardless (17 of 17 nodes at depths 2–4, catalogue-wide and under a vehicle), so the flag only adds the rest of the catalogue tree and tripled the node count for nothing the navigation reads. `maxDepth` is left unset because unset is what returns the full tree: the schema's "Defaults to 1 (no limit, full tree)" is wrong on both halves — it counts *levels* rather than edges, `1` gives the roots alone, and **`0` empties the facet**. Guessing a value here loses the categories.
- **The category options at one level overlap, and the counts never sum to the total.** TecDoc's assembly-group tree flattens several orthogonal axes into one list of roots — what a part *is*, why it is replaced, where it sits on the car. A vehicle-scoped search for "филтър" (100 articles) answers `филтър` 100 and `части за сервиз/инспекция/обслужване` with the *identical* 100 identities, while `двигател` 66, `кормилно управление` 15, `горивопроводна система` 12 and `отопление` 7 are disjoint and partition the same 100; the counts sum to 300 because each article is filed under three roots. So two options can narrow to the same list, and one covering the whole set is common (8 of 20 measured searches, never catalogue-wide — there `филтър` is 93%). This is served as it comes, because every way of collapsing it drops one of TecDoc's axes. In particular, **do not filter out a root whose count equals the total** — it is the rule dimension facets use for a single-value criterion, and on a tree it deletes the best drill path while keeping the worst (`филтър` splits into five useful kinds; `части за сервиз` into Периодична подмяна / Други).
- **`assemblyGroupNodeId` is unique across trees, so the node map is keyed on the bare id.** A catalogue-wide search spans the passenger-car and universal trees at once, and a reused number would overwrite one node with another and hang a breadcrumb off a parent from the other tree; measured over 2,277 ids from all six tree types (P, U, B, O, M, A), none is reused. The **names** are not unique, though, and that is the one thing `assemblyGroupType` is read for. Those two trees duplicate labels outright — 9 of 37 roots on `q=филтър`, 23 of 67 on `q=двигател`, with "двигател" both `100002` (passenger car, 133,828 articles) and `705972` (universal, 1) — so `qualifiedLabelsFor` suffixes the non-passenger-car side of a **sibling** collision with the tree it came from ("двигател (универсални части)"). Siblings only, because that is what one level renders side by side; the same name under two parents is told apart by where the visitor already is. Neither side is ever dropped: the bigger one is not consistently the passenger-car one ("климатична уредба" is 114 universal against 87 passenger car), so suppressing either would sometimes hide the larger category. A collision between trees we have no wording for stays unqualified rather than inventing one.
- **Ranking is live; the ranked *order* is pinned.** Reading stock is cheap enough to do per request (1.7 ms for 500 identities) and the answer changes by the minute — which is exactly why the result has to be held, and `ArticleOrderCache` holds it. `searchOrderCacheKey` gives it the enumeration's page-free identity plus the sort, so `search:order:…` answers every page of one search *in one order* from one ranking.
- **`maxPage` has two sources, and they are not interchangeable.** An ordered set is paged by us out of an enumeration we hold, so every page is reachable and `ceil(total / pageSize)` is exact. The fallback is bound by TecDoc's `maxAllowedPage` instead. `resolveMaxPage` takes the lower of the two.
- **One search is one TecDoc call, in every mode.** `searchCallFor` maps the mode to a single `SearchCall` and `SearchService` reads as parse → enumerate → page. A part-number search once attempted a second "lane" — the query as typed, in case the token stripped as a brand was really part of the number — and it was removed after measuring 127 live queries in which it never answered anything the stripped call could not. `searchType 10` reads a whole query as one number, so a two-token query matches nothing whichever lane sends it, and `prefix_or_suffix` still finds a part whose number begins with its own brand name (BSG files `BSG 70-550-001`) from the stripped `70-550-001`. Restoring a fallback means restoring the probe that decides which lane the *facets* came from — do not add one back without that.

#### What a list call asks for: never `includeAll`

**Every `getArticles` request names the fields it needs.** `includeAll` looks convenient and is the single most expensive mistake available on this API: it adds PDFs, links, linkages, parts lists, accessory lists, GTINs, prices, trade numbers and OE numbers to every row. Measured against real queries, with the mapped rows byte-identical each time:

| call | flags it needs | saving |
|---|---|---|
| Search enumeration (`search.tecdoc.ts`) | generic articles, misc — a candidate carries nothing a row renders | it is the whole point of the read: a thousand candidates cost what a hundred hydrated rows would |
| Search fallback page (`search.tecdoc.ts`) | generic articles, images, criteria | 25–58% (1,834 → 979 KB over six queries) |
| Row hydration (`article-rows.tecdoc.ts`) | the same three | 32–60% over the `includeArticleText` + `includeOEMNumbers` payload it replaced |
| Category listing (`articles.tecdoc.ts`) | the same three | 35–44% (486 → 287 KB over four pages of 20) |
| Article detail (`articles.tecdoc.ts`) | the same three **plus OE numbers**, and the assembly-group facet | 4–23%; one row, so this one is about saying what the read needs, not speed. The facet is the breadcrumb's whole cost: +986 bytes, no second call |
| `getBrands` (`brands.tecdoc.ts`) | `includeDataSupplierLogo` | 512 → 292 KB and 5× faster, same 539 logos over 619 brands |

Three facts to build a payload from:

- **Identity is free.** `articleNumber`, `dataSupplierId` and `mfrName` come back with no include flag set, so nothing has to be requested to identify a part or name its brand.
- **`legacyArticleId` lives inside `genericArticles[]`, not on the article.** `includeGenericArticles` is what carries it — the same flag that carries the description — so the id used to hydrate rows by `legacyArticleIds` costs nothing extra. `legacyArticleIdsOf` reads it; note TecDoc files one per article/generic-article pair, so a part catalogued in two roles has two.
- **What each list surface renders is exactly `mapArticleSummary`.** That is `includeGenericArticles` (description), `includeImages` (thumbnail) and `includeArticleCriteria` (specs). Nothing else. `includeMisc` is read only by the cross-reference supply-status rank, never by a summary.

**OE numbers are not on `ArticleSummaryDto` and must not be put back.** They are the bulkiest field on an article — 34 to 61 on a filter, roughly half a hydrated row — and no list renders them. They live on `ArticleCatalogDetailDto` for the detail page, and a catalog row's numbers section reads them from `/catalog/brands/:brandId/articles/:articleNumber/part-numbers` alongside the cross-reference alternatives, on one request, when a visitor opens it.

#### Paging and sorting `getArticles`

Settled from the two sources above, so none of it needs the Test Client.

- **`perPage` defaults to 10 and tops out at 1000.** The schema sets no ceiling and the guide's own examples use 100, but the live service enforces one and names it: `perPage: 2000` is refused `400` with `Field 'perPage' must be > 0 and <= 1000`. We send 1000 for the two whole-set reads — the search enumeration and the cross-reference candidate read — and 20 for the category listing and the search's fallback page. `perPage` is a cap, not a fetch size — a request costs the rows that exist, so raising it does not cost anything on a narrow result.
- **`page` reaches only the first ~10,000 results** — "exact limit subject to change". The schema offers no cursor, scroll or offset alternative, so this is a hard ceiling on any pager, not a tuning knob.
- **`maxAllowedPage` in the response is the real bound on anything TecDoc pages.** It is derived from the match count *and* `perPage`, so raising `perPage` lowers it. Never size a pager on `ceil(total / perPage)`: a broad query reports millions of matches and still refuses page 501. `resolveMaxPage` in `search/search-enumeration.ts` is the one place that decides this, and it is also where the distinction lives between a set TecDoc pages and one we page ourselves out of an enumeration.
- **`perPage: 0` returns counts and facets with no article rows** — guide §8.3 step 1 answers it with 6,943,670 matches and `articles: []`. That is the documented shape of a count-only or facet-only call.
- **`sort` is a repeatable `{ field, direction }`.** `field` is one of `score`, `mfrName`, `articleNumber`, `articleCreatedOn`, `linkageCreatedOn`, `linkageSortNum`; `direction` is `asc` or `desc`. Sent on exactly one call, `readRowsPage`, and only for the two alphabetical sorts — `tecDocSortFor` in `search.tecdoc.ts` is the one place that maps them, always sending both fields so a page boundary cannot fall inside a run of ties. Everything else sends none and takes TecDoc's relevance order. A set we enumerate ourselves is sorted by our own comparators even for those two axes, because we already hold it and a second source for one order is a second answer to it.
- **Nothing orderable or filterable in TecDoc knows what we can ship.** `includePrices` returns catalogue prices the data supplier filed with TecDoc (typed by `kindOfPriceKey`), not our sell price, and no sort field or facet touches stock. Sorting by price, availability or delivery time has to be answered from backoffice inventory over a set we hold in full — which is why the search enumerates its match set rather than sorting a page of it, why those three sorts are the ones `requiresRankedSet` names, and why they can only be offered up to `SEARCH_SORTABLE_LIMIT`.
